[4. 역할 정책]
4-1. GNSS
GNSS package 자체는 localization / sensor information 제공만 담당한다고 본다.
Pure Pursuit를 GNSS package의 책임으로 두지 않는다.
신규 architecture에서 Pure Pursuit는 반드시 control_manager 내부의
Motion Control / Lateral Control 영역에 둔다.
현재 기존 gnss_tools의 Pure Pursuit 코드는 READ ONLY 참고 가능하다.
기존 코드를 수정하지 말고,
필요하다면 control_manager 내부에 독립적인 Pure Pursuit 구현을 작성해라.
4-2. IMU
초기 baseline은 GNSS-only이다.
IMU는 optional이다.
정책:
GNSS primary
IMU optional assist
이번 작업에서 EKF를 억지로 구현하지 마라.
State Estimator가 다음 두 모드를 향후 지원 가능하도록 구조만 설계한다.
GNSS_ONLY
GNSS_IMU
기본값:
    GNSS_ONLY
fusion_enable 또는 이에 준하는 parameter 기본값:
    false
fusion=true인데 실제 fusion이 아직 구현되지 않았다면
조용히 잘못된 계산을 하지 말고 warning/error 등 명시적인 동작을 해라.
4-3. RGB Camera
RGB는 주로:
- Lane
- Traffic Light
- Traffic Sign
정보를 위한 입력으로 본다.
Lane 관련 최종 상태는 VehicleState에 섞지 말고 LanePose로 분리한다.
LanePose 기본 요소:
lateral_error_m
heading_error_rad
confidence
valid
timestamp
현재 lane_AI는 numeric lane state를 제어로 보내지 않으므로
실제 lane extraction을 이번 작업에서 임의 구현하지 마라.
향후 LanePose publisher를 붙일 수 있게 interface만 설계한다.
4-4. Depth Camera
Optional sensor.
향후:
- near-field obstacle 보조
- object validation
등에 사용할 수 있도록 topic/config/interface 자리는 두되,
현재 제어 필수 센서로 만들지 마라.
4-5. LiDAR
Obstacle의 Primary Sensor이다.
팀 회의 결과:
    Obstacle -> LiDAR
로 사용한다.
이번 작업에서는 실제 clustering/detection은 구현하지 않고
object_manager의 obstacle interface skeleton만 만든다.

[5. State 정의]
세 가지 상태는 반드시 논리적으로 분리해라.
VehicleState
ego vehicle 자체 상태.
최소 개념:
x_m
y_m
yaw_rad
speed_mps
yaw_rate_radps
localization_valid
timestamp
yaw_rate는 IMU 미사용 시 유효하지 않을 수 있다.
VehicleState는 control_manager 내부 C++ type으로도 사용 가능해야 한다.
또한 여러 ROS node 사이에 전달할 수 있도록
/control/vehicle_state
형태의 topic contract도 제공해라.
필요하다면 control_manager package 내부에 custom msg를 정의해도 된다.
외부 interface package는 만들지 마라.
control_manager 밖에 새 package를 만들지 마라.
LanePose
도로/차선에 대한 상대 상태.
최소 개념:
lateral_error_m
heading_error_rad
confidence
valid
timestamp
topic 예:
    /control/lane_pose
ObjectState
외부 object / traffic 상태.
이번에는 확장 가능한 최소 skeleton만 만들어라.
향후 최소 포함 예정:
traffic light state
speed limit
obstacle detected
nearest obstacle distance
validity
timestamp
ObjectState 상세 필드는 과도하게 확정하지 말고
확장 가능하도록 기본 틀 위주로 설계해라.
topic 예:
    /control/object_state

[8. mission_based_limit]
기존의 "map mission context / rule based behavior" 개념의 이름은
mission_based_limit으로 사용한다.
역할:
정상적인 주행 규칙과 mission에 따른 제한 생성.
예:
- 일반 구간 max speed
- curve/turn 구간 감속
- traffic light 구간에서 RED이면 stop required
- speed limit sign 반영
- 특정 mission section의 정책 반영
이 module은 직접 steering을 계산하지 않는다.
개념적인 출력 예:
max_speed_mps
stop_required
validity / reason
현재 mission section 세부 rule은 확정하지 않았으므로
과도한 hard coding은 하지 마라.
확장 가능한 skeleton을 작성해라.

[9. safety_limit]
mission_based_limit와 safety_limit는 반드시 구분한다.
mission_based_limit:
    정상적인 주행 규칙에 따른 제한
safety_limit:
    위험 / 시스템 이상에 따른 최종 제한
예:
- localization stale
- invalid state
- command timeout
- E-STOP
- obstacle emergency distance
- invalid command
- steering command 범위 초과
- speed command 범위 초과
Safety는 AUTO / MANUAL 선택보다 최종적으로 높은 우선순위를 가진다.
즉:
AUTO/MANUAL command 선택
        |
        v
   safety_limit
        |
        v
   FinalCommand
구조로 만들어라.

[11. Motion Control]
Motion Control 입력:
VehicleState
MotionPlan
출력:
AutoCommand
AutoCommand의 기본 개념:
target_steer
target_speed
target_brake
단위는 내부에서 물리 단위를 명확히 사용해라.
권장:
steering : deg 또는 rad 중 한 가지로 일관
speed    : m/s
brake    : bool (초기)
UDP raw 단위와 내부 물리 단위를 섞지 마라.
Lateral Controller
Baseline은 Adaptive Pure Pursuit.
현재 기존 gnss_tools Pure Pursuit를 READ ONLY 분석하여
필요한 개념을 control_manager 내부에 독립적으로 구현한다.
현재 실측 wheelbase:
    1.328 m
Stanley / LQR / MPC는 구현하지 마라.
향후 lateral controller를 교체할 수 있는 정도의 clean interface만 고려한다.
Longitudinal Controller
현재 실제 vehicle speed raw contract가 확정되지 않았다.
따라서 검증되지 않은 PID나 raw conversion을 임의 구현하지 마라.
이번에는 MotionPlan의 target_speed를
AutoCommand의 물리 단위 target_speed_mps로 전달할 수 있는
기본 구조만 만든다.

[12. AUTO / MANUAL]
ControlMode:
IDLE
MANUAL
AUTO
AUTO:
    motion_control_node의 AutoCommand 사용
MANUAL:
    keyboard/manual command 사용
ManualCommand와 AutoCommand는 최종적으로 동일한 VehicleCommand 의미로
변환 가능해야 한다.
control_manager_node가 mode에 따라 command source를 선택한다.
MANUAL mode에서는 AUTO drive command를 선택하지 않는다.
AUTO mode에서는 MANUAL drive command를 선택하지 않는다.
단 E-STOP / safety override는 mode와 무관하게 적용 가능해야 한다.
실제 keyboard reader를 과도하게 구현하지 않아도 된다.
필요하면 manual command topic/interface skeleton을 먼저 만들어라.

[14. Vehicle Interface / UDP]
최종 목표는 actuator sender를 하나만 두는 것이다.
기존:
    guidance 직접 UDP
    trans 직접 UDP
가 존재하지만 해당 파일을 절대 수정하지 마라.

최종 actuator interface ownership 지점으로 설계한다.
단 이번 작업에서 실제 차량을 움직이는 UDP를 무조건 활성화하지 마라.
기본:
    dry_run = true
dry_run=true:
- Final VehicleCommand까지 계산 가능
- topic/log 출력 가능
- 실제 UDP 송신 금지
dry_run=false:
- 향후 검증된 packet/scale/unit 계약이 있을 때만 사용
현재 raw speed 계약과 실제 motor firmware 상태가 불명확하므로
잘못된 conversion을 추정하여 작성하지 마라.

[15. 실측 Vehicle Configuration]
아래 값은 최근 실측한 값이며 신규 config에서 우선값으로 사용해도 된다.
단위는 코드/config 내부에서는 SI 단위(m)를 권장한다.
vehicle:
    length_m: 2.222
    width_m: 1.280
    height_m: 1.3005
rear_axle_from_rear_m: 0.225
front_axle_from_rear_m: 1.553

wheelbase_m: 1.328
track_width_m: 1.060
Rear axle center를 차량 제어 기준점(base reference)으로 사용하는 방향을 우선한다.
LiDAR 실측:
    rear 기준 x = 0.784 m
    rear axle 기준 x = 0.784 - 0.225 = 0.559 m
    z = 1.224 m
차량 중심선 장착으로 가정 가능한 경우:
    y = 0.0
단 실제 y 측정 근거가 없다면 주석으로 명시할 것.
Camera 실측:
    rear 기준 x = 0.861 m
    rear axle 기준 x = 0.861 - 0.225 = 0.636 m
    z = 1.140 m
마찬가지로 y는 실제 확인 전에는 assumption임을 명시한다.
다음 값은 아직 실차 확정되지 않았으므로 임의 확정 금지:
- actual max steering angle
- steering command <-> actual wheel angle calibration
- physical max operating speed
- GNSS sensor exact xyz/RPY
- IMU exact xyz/RPY
- Camera/LiDAR rotation extrinsic
- motor raw <-> m/s
- brake physical model
안전-critical한 미확정 parameter는
기존 repository 값을 실제값인 것처럼 조용히 사용하지 마라.
필요하면 TODO / NOT_VERIFIED 상태를 config/README에 명시한다.

[16. Config 정책]
control_manager가 사용하는 모든 제어 관련 parameter는
control_manager/config/ 아래에 모은다.
외부 package와 값이 중복되어도 괜찮다.
새 stack이 실행될 때 control_manager config를
새 제어 stack의 local source of truth로 본다.
다만 parameter의 출처/신뢰도를 주석으로 남겨라.
예:
wheelbase_m: 1.328       # MEASURED
track_width_m: 1.060     # MEASURED
미확정값은:
# TODO: NOT_MEASURED
# TODO: NOT_VERIFIED
처럼 명시한다.
vehicle geometry와 control parameter를 분리하는 것이 깔끔하면:
config/vehicle.yaml
config/control.yaml
로 나누어도 된다.
기존 control_manager.yaml과 충돌하지 않도록
패키지 내부에서 일관되게 정리하고 launch도 함께 갱신한다.
