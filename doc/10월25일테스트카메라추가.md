# 10월 25일 테스트 카메라 추가

기존 [10월25일테스트신규.md](10월25일테스트신규.md)의 터미널 1~7은 그대로 사용하고,
카메라와 카메라 전용 기록 터미널을 추가한다. 기존 카메라가 실행 중이면 재사용한다.
카메라 기록은 기존 센서·제어 기록과 별도 프로세스·큐·bag으로 저장한다.

`/camera/image_raw/compressed`의 JPEG와 원래 `header.stamp`를 CDR 그대로 보존한다.
디코딩·재인코딩·실시간 MP4 변환은 하지 않는다. 원본 영상 토픽은 기록하지 않는다.
카메라 기본 설정은 1280×720, 30fps, JPEG 품질 80이며 입력 프레임을 임의로 줄이지 않는다.
카메라가 새로 실행되면 기존 카메라 코드의 원본 영상 생성·JPEG 인코딩 부하도 추가된다.

## 1. 공통 준비

아래는 차량 PC 호스트에서 실행한다. 기존 `vehicle_recorder record`와 `camera camera`가
설치된 현재 환경에서는 설정·스크립트 추가만으로 동작하므로 재빌드가 필요 없다.

각 추가 터미널에서 다음을 실행한다. 이후 명령은 컨테이너 안이다.

```bash
docker exec -it \
  -e CONTROL_IMAGE_ID="$(docker inspect --format '{{.Image}}' main)" \
  -e CONTROL_CONTAINER_ID="$(docker inspect --format '{{.Id}}' main)" \
  main bash
cd /workspace
source /opt/ros/humble/setup.bash
source /workspace/install/setup.bash
export TEST_ROOT=/workspace/log/autonomy_new_20261025
```

## 2. 터미널 8 — 카메라

이미 카메라가 켜져 있으면 이 단계는 생략한다. 카메라는 한 번만 실행한다.

```bash
export TEST_ROOT="${TEST_ROOT:-/workspace/log/autonomy_new_20261025}"
export ROS_LOG_DIR="$TEST_ROOT/ros/camera-$(TZ=Asia/Seoul date +%Y%m%dT%H%M%S)-$$"
mkdir -p "$ROS_LOG_DIR" && \
ros2 run camera camera --ros-args \
  -p device:=/dev/video0 \
  -p width:=1280 -p height:=720 -p fps:=30.0 -p jpeg_quality:=80
```

## 3. 터미널 9 — 카메라 전용 기록

공통 준비 후 실행한다. 발행자 1개와 메시지 형식을 확인한 뒤 기록한다.
같은 저장 루트의 중복 실행과 이미 실행 중인 `camera_recorder`는 거부한다.

```bash
bash /workspace/tools/record_camera.sh
```

`Recording serialized /camera/image_raw/compressed [sensor_msgs/msg/CompressedImage]`를
확인한 뒤 출발한다. `기록 폴더`만 표시되고 위 구독 메시지가 없으면 출발 전 상태를 확인한다.
기존 터미널 4의 센서·제어 기록도 켜져 있어야 한다.

전용 설정은 `vehicle_recorder/config/record_camera.yaml`이다.

- 카메라 저장 큐: 최대 64개 또는 32MiB 중 먼저 도달하는 한도.
- DDS 구독 depth: 8. 실제 카메라 발행 QoS에 맞춰 구독한다.
- CPU nice: 10. 기존 제어·센서 프로세스보다 낮은 우선순위로 실행한다.
- DDS 전송: 기존 main의 16MiB SHM 프로필을 사용한다. 환경변수가 없으면 스크립트가
  `/workspace/src/lidar/config/fastdds_shm_profile.xml`을 기본값으로 적용한다.
  명시한 프로필은 덮어쓰지 않는다.
- 저장 지연 시 큐를 무한히 늘리지 않는다. 큐 초과·감지된 DDS 손실·저장 오류는
  카메라 기록 실패로 남기고 해당 기록 프로세스만 종료한다.
- 이미지 인터페이스·설정·카메라 소스·기록 스크립트를 함께 보존한다.
  카메라 파라미터를 변경한 시험은 실행 명령도 함께 남긴다.

프로세스 분리는 큐와 실패 처리를 분리한다. CPU·메모리·디스크·USB 자원은 공유하므로
주기 영향이 없다는 보장은 아니며, nice는 CPU 우선순위만 조정한다.

## 4. 종료와 저장 위치

1. 터미널 7에서 `3/Q`로 정지 요청하고 실측 정지·콘솔 종료를 확인한다.
2. 터미널 9에서 `q`로 카메라 기록을 닫고 `y/n`과 시험 이름을 입력한다.
3. 터미널 4도 `q`로 닫고 같은 시험 이름을 입력한다.
4. 카메라와 송신기, 센서를 종료한다. 카메라 발행은 기록을 닫을 때까지 유지한다.

`Ctrl+C`도 저장 큐를 비우고 닫지만 이름 확인 절차는 생략된다. 오류가 표시된 기록은
`y`로 이름을 붙여도 `metadata.json`의 `complete`가 정상으로 바뀌지는 않는다.

호스트 저장 위치:

```text
/home/baqu4/Workspaces/2026WS/main/log/autonomy_new_20261025/
  records/         기존 센서·제어·송신 이벤트
  camera_records/  카메라 전용 bag, receipts.csv, metadata.json
  console/        자율주행 콘솔·명령·설정
  ros/            카메라·터미널별 ROS 로그
```

두 기록에 동일한 시험 이름을 붙이고, 사후에는 카메라 `header.stamp`와
GNSS·제어 메시지 시각으로 대응한다. 별도 bag이므로 시작·종료 시각은 완전히 같지 않다.

## 5. 종료 후 카메라 저장 확인

컨테이너 안에서 실행한다. 최근에 갱신된 카메라 세션을 검사한다.

```bash
python3 - <<'PY'
import json
import os
from pathlib import Path

root = Path(os.environ.get('TEST_ROOT', '/workspace/log/autonomy_new_20261025'))
files = list((root / 'camera_records').glob('*/metadata.json'))
assert files, '카메라 기록이 없습니다.'
path = max(files, key=lambda p: p.stat().st_mtime_ns)
m = json.loads(path.read_text())
b = m.get('backend', {})
t = b.get('topics', {}).get('/camera/image_raw/compressed', {})
print('기록:', path.parent)
print('complete:', m.get('complete'), 'closed:', b.get('closed'))
print('수신:', t.get('received', 0), '저장:', t.get('written', 0))
print('미발견:', m.get('undiscovered_topics'), '오류:', m.get('errors'))
print('최대 저장 큐 MiB:', b.get('peak_queue_bytes', 0) / 1024**2)
assert m.get('complete') and b.get('closed'), '기록이 아직 열려 있거나 실패했습니다.'
assert not m.get('undiscovered_topics'), '미발견 토픽이 있습니다.'
assert t.get('written', 0) > 0 and t['received'] == t['written'], '영상이 없거나 수신·저장 건수가 다릅니다.'
assert b.get('pending') == 0 and not m.get('errors'), '저장 대기 또는 오류가 있습니다.'
print('카메라 수신 데이터 저장 확인 완료')
PY
```

`complete`와 수신·저장 건수 일치는 기록기 수신 이후 저장 확인이다.
카메라 촬영부터 DDS 전달까지 모든 프레임의 무손실을 증명하는 값은 아니다.

## 6. 부하 비교

동일한 센서·제어 구성에서 카메라는 켜 둔 채 카메라 기록 OFF/ON을 비교한다.
카메라 자체의 추가 부하는 카메라 OFF/ON 비교로 따로 확인한다.
최소 1분씩 기록하고 다음을 비교한다.

- 제어 명령·PC 송신: 약 50Hz 유지 여부와 최대 간격·100ms 초과 공백.
- 경로·상태: 약 20Hz 유지 여부와 최대 간격.
- GNSS: 평균 20Hz 외에 기존 약 300ms 공백이 더 길어지는지 확인.
- 모터·조향: 토픽 Hz와 MCU tick 갱신 간격·invalid 상태를 함께 확인.
- 기록: 양쪽 `metadata.json`의 `complete`, 오류, pending, peak_queue_bytes 확인.

평균 Hz만으로 통과 판정하지 않는다. 이번 격리 시험은 기록 분리와 저장 정확성 검증이며,
실제 카메라·센서·제어 전체 부하에서 주기 영향이 없다는 인증은 아니다.

검증 자료는 호스트 `test_runs/camera-recording-20261025/`에 보존했다.
동일 이미지의 네트워크 분리 임시 컨테이너에서 720p JPEG 30fps 120프레임의
CDR·원래 헤더 시각 일치, 별도 제어 기록 300건의 저장, 카메라 큐 초과 시 제어 기록
유지, 카메라 미실행·기록 중복 실행 거부를 검사한다.

## 7. 본선 시작 구간 우선 연결 (15시 시험 후 수정)

`final_lap.yaml`의 속도 계획·조향 제어 양쪽에서 본선 6787점 진행 위치 추적을 활성화했다.
처음에는 경로 첫 10m에서만 연결하고, 이후 진행 위치에서 뒤 3m·앞 10m를 검색한다.
일시정지·센서 일시 오류 후에도 같은 실행에서는 진행 위치를 유지한다.
가까운 종점 구간을 최초 위치로 선택하지 않으며, 새 실행은 다시 시작 구간에서 연결한다.

재빌드는 필요 없다. 터미널 7에서 `3/Q`로 종료한 뒤, 기존 설정 사본을 재사용하지 말고
설정 생성 부분부터 다시 실행한다. 생성 원본과 콘솔 인자는 아래처럼 본선으로 맞춘다.

```python
source = Path('/workspace/src/control_manager/config/modes/final_lap.yaml')
```

기존 콘솔 명령 중 아래 인자를 사용하고, 속도·가감속 등 나머지 시험값은 유지한다.

```bash
  --mode final_lap \
  --operation-file "$CONTROL_TRIAL_OPERATION" \
  --map-file /workspace/decision/script/map_generator/test/review/maps/MAP_final.json \
  --variable-speed \
  --max-path-distance-m 0
```

위 블록은 기존 `ros2 run control_manager control_console` 명령의 인자 부분이다.
실제 출력용 설정 생성 줄 `data['/control/vehicle_interface']['ros__parameters']['dry_run'] = False`도 유지한다.
소스의 `final_lap.yaml` 기본값 `dry_run: true`를 직접 실행하면 실제 출력은 하지 않는다.

기록된 출발 위치에서 지도 첫 점까지는 약 58m다. 시작 구간 우선 연결은 지도 점을 이동하거나
실제 출발선으로 다시 정의하지 않는다. 기존 `--max-path-distance-m 0`을 빠뜨리면 이 위치는
기본 거리 제한 3m 밖이므로 계획이 정지한다. 이 옵션은 거리 제한만 해제하며
시작 구간 검색 범위와 진행 순서 제한은 유지된다. 당시 기록의 경로·위치를 이용한 재구성에서
수정 전 종점 쪽 선분 선택·PP 실패가 수정 후 시작 선분 선택·유효한 PP 계산으로 바뀌는지 검증한다.
